# Перенос на Windows и другой аккаунт Cloudflare

Подготовлено 28.10.2026 для планируемого переноса 29.10.2026.
Создаётся новое приложение с новой общей D1-базой, прежними данными и
пользователями. URL изменится. Старое приложение сохраняется для отката.

## 1. Скачать проект

В закрытом репозитории `vlad-ultra/Glasfaser-WebApp`, раздел Releases,
скачать `Glasfaser-Migration-Windows-2026-10-28.zip` из релиза
`migration-2026-10-28`. Нужен вход GitHub с доступом к репозиторию.

Распаковать: внутри папка `Glasfaser-WebApp/` с исходниками и
`.private/migration-2026-10-28/database.gfb`, а также
`database.gfb.manifest.json`. Манифест содержит SHA-256, время экспорта,
ревизию и количества записей. ZIP содержит реальные данные и парольные
хеши — передавать только участникам переноса.

Если код клонируется отдельно, скачать данные из Release и положить их
с манифестом в указанную папку. В исходниках Git данных нет.

Установить Node.js 22+; Git нужен только при клонировании. Открыть Claude
в распакованной папке: контекст находится в `CLAUDE.md`.

```powershell
Set-Location "C:\Users\YOUR_NAME\Downloads\Glasfaser-WebApp"
node --version
npm ci
npm test
npm run build
```

При блокировке `npm.ps1` использовать `npm.cmd`/`npx.cmd`, например
`npm.cmd ci`. Менять системную политику выполнения не нужно.

## 2. Получить свежие данные перед переключением

Архив содержит снимок на время экспорта 28.10.2026. Если после этого работали:

1. Попросить пользователей закончить, дождаться «Облако: всё сохранено»
   и закрыть приложение на всех устройствах.
2. На компьютере с доступом к ИСХОДНОМУ аккаунту выполнить команду ниже.
3. Передать новый `.gfb` и его `.manifest.json` на Windows.
4. До переключения не возобновлять ввод в старом приложении.

```text
npm run cloud:backup -- --output .private/final-cutover/database.gfb
```

Команда только читает исходную базу. Снимок согласован в рамках одного
SQL-запроса и включает все прикладные записи/парольные хеши. Сеансы и
Cloudflare OAuth-токены не переносятся. В новом приложении все входят заново.
После смены аккаунта для свежего экспорта понадобится доступ к старому аккаунту
или помощь его владельца.

## 3. Авторизация и новая база

`NEW_ACCOUNT_ID` и `NEW_DATABASE_UUID` ниже заменить реальными значениями
НОВОГО владельца. ID из старого wrangler.jsonc не подходят.

```powershell
npx wrangler login
npx wrangler whoami
```

Владелец сам входит и разрешает доступ в браузере. Проверить account ID
в whoami или Dashboard. Создать конфигурацию только нового аккаунта:

```powershell
npm run cloud:account -- --account-id NEW_ACCOUNT_ID
npx wrangler d1 create glasfaser-migrated --jurisdiction eu --config wrangler.account.json
```

Взять UUID из ответа и создать отдельную конфигурацию развёртывания:

```powershell
npm run cloud:target -- --account-id NEW_ACCOUNT_ID --database-id NEW_DATABASE_UUID --name glasfaser-migrated --database-name glasfaser-migrated
```

Проверить account_id/database_id в `wrangler.migration.json` перед продолжением.
Скрипты не перезаписывают существующие конфиги: если файл есть, остановиться
и проверить его. Исходный wrangler.jsonc остаётся нетронутым.

## 4. Восстановить в пустую D1

```powershell
npx wrangler d1 migrations apply glasfaser-migrated --remote --config wrangler.migration.json
npm run cloud:restore -- --backup .private/migration-2026-10-28/database.gfb
```

Для свежего снимка заменить путь. Restore проверяет SHA-256 по манифесту,
пустоту назначения, запрещает исходный UUID, импортирует и сравнивает ВСЕ
записи с файлом. При ошибке не публиковать и не переключать пользователей.
Не обходить защиту и не очищать чужую существующую базу для повторной попытки.

Схема и первоначальный seed применяются к новой базе один раз. Не использовать
браузерное «Восстановить» для первоначальной миграции: нужен серверный импорт
с сохранением парольных хешей.

## 5. Опубликовать

```powershell
npm run build
npx wrangler deploy --config wrangler.migration.json
```

**Не запускать `npm run deploy` при переносе:** он использует старый конфиг.
Все удалённые команды должны явно указывать конфигурацию нового аккаунта.
При первом запуске выбрать поддомен workers.dev и сохранить URL из ответа.
Активация HTTPS может занять некоторое время; сертификатные ошибки не обходить.

## 6. Проверить и переключить пользователей

- Без входа видна форма; `/api/state` отвечает 401.
- Пользователь с заданным паролем входит с прежними данными.
- Данные всех разделов и количество записей совпадают с последним манифестом.
- В настройках верно показано, кому задан пароль. У тех, у кого пароля не было,
  он автоматически не появляется; администратор задаёт его при необходимости.
- Сохранить тестовое изменение на одном устройстве, проверить второе,
  затем убрать тестовое изменение штатным способом.
- Убедиться в статусе «Облако: всё сохранено» на обоих устройствах.
- Раздать новый URL и прекратить ввод через старые вкладки/закладки.

Последующие обновления нового приложения также публиковать с
`npx wrangler deploy --config wrangler.migration.json`.
Зафиксировать новый URL и ID аккаунта в документации после успешного переноса.

## Откат

Старая база и публикация сохранены. Если в новой базе ещё не начали работать,
вернуть пользователей на старый URL. Если в новой базе уже появились записи,
сначала экспортировать обе базы: потребуется объединение изменений. Не
импортировать старый снимок поверх новой рабочей базы. Две базы после переноса
сами не синхронизируются.
